# 乐高积木式模块化架构与旧项目防屎山改造标准规程（SOP）

本技能定义了全栈项目从第一行代码起的**乐高积木式（Lego-Brick）模块化铁律**、接入历史遗留庞大耦合代码（俗称“屎山代码”）时的**双模式安全改造工作流**，以及用于消除跨会话上下文迷失的**活体代码地图（`memory/CODE_MAP.md`）全自动维护规范**。

所有架构设计、代码新增、模块拆解与遗留系统重构，必须 100% 严格遵循本规程。

## 一、 乐高积木式模块化铁律（Lego-Brick Modularity from Day 1）

### 1.1 核心设计哲学：按逻辑零件拆分，绝不死等行数爆炸
* **第一行代码即模块（Day-1 Modularity）**：**严禁等待单个文件膨胀到几百上千行后才被动拆分！** 只要某个功能在逻辑上属于一个独立的“小零件”（例如：一个独立的 UI 视图卡片/弹窗组件、一个独立的数据表访问层 DAO/Repository、一个独立的领域业务计算服务、一个独立的第三方 API/硬件/存储适配器、一组内聚的校验或格式化工具函数），从写下第一行代码起，就必须将其创建为独立的文件模块。
* **单一职责铁律（Single Responsibility Principle, SRP）**：每个文件模块只能有一个引起它变化的原因。
  * **严禁跨层混写**：绝不允许在同一个文件内既写 UI 渲染逻辑、又写网络请求拼装与状态清洗，或者在后端路由控制器（Controller）中直接编写复杂的业务规则与底层 SQL 语句。
  * **高内聚、低耦合**：模块内部状态与辅助函数默认私有（不导出），仅通过清晰、最小化的接口（Explicit Export / Interface）向外部暴露能力。
  * **显式导入导出**：全面禁止通过隐式全局变量（如 `window.*`、`global.*` 或未声明的单例属性挂载）在模块间传递数据或函数；所有依赖必须通过语言标准的 `import / export` 或依赖注入（DI）显式声明。
* **行数预警与熔断防线（全系统统一标准：300 行黄灯 / 500 行红灯）**：
  * 虽然拆分以“逻辑独立性”为第一准则，但仍设硬性兜底防线：单文件建议控制在 **150~300 行以内**；一旦单文件超过 **300 行（黄灯软预警）** 必须审视是否存在多职责混杂；除自动生成的协议/类型定义文件与独立运维脚本外，任何**新建或已拆解的业务源码模块**单文件严禁突破 **500 行（红灯硬熔断）**。
  * **【防死循环特例：模式 B 存量历史大文件豁免法则】**：若用户在旧项目改造中选择了 **模式 B（童子军渐进抽离法则）**，对登记在 `memory/CODE_MAP.md` 第五节中的存量历史大文件（如原本就有 2000 行的遗留文件），执行 **「行数只减不增（Strictly Non-Increasing）」** 守卫——只要本次将触碰到的新逻辑抽离为 $\le 300$ 行的独立新模块且原文件未净增行数，即视为合规通过，严禁违背用户意愿强行全量拆分而陷入死循环！
* **3D 交互式知识图谱与 Ponytail「7 级化繁为简」自动化协同（v3.0 升级，含 `EVO-015` 三合一交付铁律）**：
  * **修改前先查爆炸半径（Blast Radius）**：在拆解大模块或修改公共接口前，自动调用 MCP `code_graph_blast_radius`（或运行 `scripts/code-graph-3d-generator.mjs`），精准识别 2 跳上下游影响面、核心枢纽（God Nodes）与循环依赖，并生成 `<PROJECT_ROOT>/memory/CODE_GRAPH_3D.html` 3D 可旋转星系图。
  * **`CODE_GRAPH_3D.html` 三合一交付防源码展示铁律（`EVO-015`）**：在 Antigravity IDE 聊天框中直接点击 `[CODE_GRAPH_3D.html](file:///...)` 会被 IDE 当成代码文本打开显示源码！向用户展示 3D 图谱时，必须：① 传入 `open_in_browser: true`（或 CLI `--open`）自动在用户系统默认浏览器中弹出 3D 交互页；② 用无头浏览器截取 `.png` 视觉预览图附在汇报中供 IDE 内直接点击看图；③ 附上终端一键重开口令 `open "<HTML绝对路径>"`。
  * **写新函数前先查「现成可复用轮子速查表」**：写任何辅助函数前，必须先查阅 `<PROJECT_ROOT>/memory/GRAPH_REPORT.md` 自动生成的 **「本项目现成可复用轮子速查表（Reusable Helpers Registry）」**，优先复用项目已有工具函数与语言原生 API（Ponytail 第 1~2 级），并调用 MCP `security_simplicity_audit` 自动清除 1 行无意义透传包装（`PONY-01`）与死代码导出（`PONY-02`）。
  * **读写模块前先做路径核验（Pre-Read File Verification，`EVO-020`）**：调用 `read_file` 或 `edit_file` 前，必须先查阅 `CODE_MAP.md` 或通过轻量命令（`find` / `ls` / `git ls-files`）实证确认目标文件真实物理路径；严禁凭框架习惯直觉盲猜相对路径（如凭空脑补 `app/services/` 或 `src/`），严禁在同 turn 内并发盲读未经实证的多文件。

### 1.2 全栈标准目录分层规范（Standard Layered Architecture）

无论采用何种具体编程语言或框架，全栈项目必须严格遵循以下逻辑分层与单向依赖流向（上层仅可调用相邻下层，严禁下层反向依赖上层或跨层越权调用）：

```text
project-root/
├── frontend/                     # 【前端应用层】视图渲染与用户交互
│   └── src/
│       ├── pages/ (或 views/)    # 页面级路由容器：仅负责组装布局与分发页面级状态，不写复杂业务与长段UI
│       ├── components/           # 乐高 UI 零件库：按「通用基础组件 (ui/)」与「业务领域组件 (domain/)」拆分
│       ├── hooks/ (或 composables/) # 状态逻辑抽离层：封装独立的交互状态机、表单联动与生命周期副作用
│       ├── services/ (或 api/)   # 接口通信适配层：统一封装 HTTP/WebSocket 请求、DTO 转换与错误拦截
│       ├── stores/               # 全局/跨组件状态层：仅存放真正需要跨页面共享的领域状态
│       ├── types/                # 显式数据结构与接口契约定义
│       └── utils/                # 纯函数工具库（无副作用、无业务状态依赖，如日期格式化、数值计算）
│
├── backend/                      # 【后端服务层】业务编排与领域核心
│   └── src/
│       ├── api/ (或 controllers/, routes/) # 传输控制层：仅负责路由挂载、请求参数校验、调用 Service 与统一响应封装
│       ├── services/             # 核心业务逻辑层：每个独立业务域一个模块，编排领域规则与事务
│       ├── repositories/ (或 dao/) # 数据持久化访问层：封装对数据库的增删改查，向上屏蔽具体 SQL/ORM 细节
│       ├── adapters/ (或 integrations/) # 外部系统适配层：第三方接口、消息队列、邮件/短信、文件系统等独立封装
│       ├── models/ (或 schemas/, entities/) # 数据模型与入参/出参 Schema 契约
│       ├── middlewares/          # 切面拦截层：鉴权、日志、限流、全局异常捕获
│       ├── config/               # 配置收敛层：环境变量解析与只读配置导出（严禁在业务代码随处散落读取环境变量）
│       └── utils/                # 后端纯函数工具零件
│
├── database/                     # 【数据库与存储层】结构演进与数据契约
│   ├── migrations/               # 版本化增量迁移脚本（严禁直接手工修改生产表结构而不留存迁移脚本）
│   ├── seeds/                    # 初始化基准数据与测试字典数据
│   └── schemas/                  # 数据库 ER 说明与核心视图/索引定义
│
├── scripts/                      # 【工程化与运维脚本层】自动化支撑
│   ├── snapshot-and-rollback.sh  # 全量快照备份与一键回滚脚本
│   ├── build-and-sync.sh         # 构建产物同步脚本（确保唯一真源单向输出）
│   └── verify-equivalence.sh     # 1:1 等价性回归校验与健康检查脚本
│
└── memory/                       # 【项目活体记忆中心】
    └── CODE_MAP.md               # 活体代码地图（实时记录模块职责、关键函数行号区间、依赖关系与唯一真源）
```

## 二、 旧项目（历史万行屎山代码）接入的双模式安全改造工作流

当接手一个包含超大单文件（如数千乃至上万行的全耦合脚本/页面）、缺乏分层、多处复制粘贴或存在隐式全局依赖的历史旧项目时，**严禁在未建立安全锚点和未经用户审批的情况下直接动刀修改代码**。必须严格按以下工作流执行：

### Step 0：强制全量基线备份与一键回滚锚点（Mandatory Baseline Backup）

在接入旧项目并对任何代码文件动第一刀之前，**必须首先执行全量快照备份**：

1. 调用项目备份脚本执行完整基线归档：
   ```bash
   bash scripts/snapshot-and-rollback.sh backup "pre-refactor-baseline"
   ```
   *(注：若旧项目尚未初始化 `scripts/snapshot-and-rollback.sh`，必须在动任何业务代码前先行创建该安全脚本并完成首次备份验证。)*
2. 获取备份归档路径与对应的一键回滚指令（例如：`bash scripts/snapshot-and-rollback.sh rollback <snapshot_id>`）。
3. **向用户明确输出安全承诺**：在对话或审批前清晰告知用户——*“已完成全量代码与数据基线快照备份（快照 ID：`xxx`）。无论后续改造处于任何阶段，您随时可以使用一键回滚命令在 1 秒内将项目 100% 恢复至当前初始状态。”*

### Step 1：屎山诊断与「全程审批」改造模式选择（Diagnosis & Mode Selection）

1. **自动化扫描与屎山诊断**：
   在进行任何修改前，自动扫描工作区，识别并汇总以下架构坏味道（Code Smells）：
   * **超大耦合文件**：统计行数超标（如 `> 300` 行）或单个文件内混杂了 UI、网络请求、业务逻辑、数据库操作的文件清单及各自精确行数。
   * **隐式耦合与全局污染**：跨职责直接读写全局变量、硬编码配置散落点。
   * **疑似阴阳副本文件**：文件名相似（如 `xxx_old`、`xxx_copy`、`dist/` 与 `src/` 手工双改文件）或内容高度重复的多份代码。
2. **弹窗征询用户选择改造模式（强制调用 `ask_question`）**：
   生成简明直观的《旧项目架构体检摘要》，并**必须通过 `ask_question` 工具弹窗**向小白用户提供两种标准化改造模式供其拍板决策，严禁自行假设或跳过询问：

   * **【标准 `ask_question` 提问结构示例】**：
     * **问题（question）**：`检测到当前项目存在历史耦合大文件（共 X 个文件超过标准体积，最大文件达 Y 行）。已完成 1 秒一键回滚快照备份。请选择接下来的安全改造与开发模式：`
     * **选项 1（推荐需彻底根治时）**：`(Recommended) 模式 A：全量标准化改造 + 1:1 等价性复现验收（先不改业务功能，将大文件按职责拆解为标准乐高积木模块，通过自动化对比确保接口与界面 100% 无损一致后，再开发新需求）`
     * **选项 2（推荐需快速迭代时）**：`模式 B：童子军渐进抽离法则 Boy Scout Rule（在执行当前业务需求的同时，凡是触碰到的大文件代码块，顺手安全抽离为独立子模块并逐项经您审批，逐步消灭屎山）`

---

### Step 2A：模式 A 执行规程（全量标准化改造 + 1:1 等价性复现验收）

当用户选择 **模式 A** 时，严格遵循**“重构期间冻结业务变更、先无损拆解、再等价验收、最后迭代新功能”**的铁律：

1. **冻结业务逻辑**：在拆解阶段，严禁顺手修改任何既有业务计算公式、接口字段名、状态码或 UI 视觉表现，确保行为基准 100% 恒定。
2. **制定拆解蓝图并弹窗审批**：
   * 列出拟拆解的大文件、拆出后的目标积木模块路径列表、每个模块的单一职责说明，通过 `ask_question` 请用户审批确认拆解蓝图。
3. **录制改造前基线快照（Golden Master Snapshot）**：
   * **后端/脚本**：针对核心 API 路由或业务函数，录制标准测试输入对应的响应 Payload、HTTP 状态码及数据库记录快照。
   * **前端/UI**：记录关键页面的 DOM 结构特征、控制台零报错基线、网络请求序列及关键交互状态变更。
4. **按乐高标准剥离模块**：
   * 按照 `utils/`（纯工具） $\rightarrow$ `models/types/`（数据契约） $\rightarrow$ `repositories/adapters/`（底层数据与外部适配） $\rightarrow$ `services/hooks/`（核心业务与状态逻辑） $\rightarrow$ `components/controllers/`（顶层视图与路由入口）的**自底向上顺序**逐层剥离。
   * 每次剥离后保持原入口调用签名兼容，通过显式 `import/export` 重新组装。
5. **1:1 等价性复现自动化验收（1:1 Equivalence Verification）**：
   * **接口输入输出 100% 一致**：运行基线对比测试，确保相同时序输入下，所有 API 返回的 JSON 结构、字段类型、边缘异常响应与改造前基线 100% 字节级/语义级一致。
   * **UI 渲染与交互 100% 一致**：验证页面布局渲染、组件状态流转、表单提交与事件触发与改造前完全一致，且编译构建与运行期实现 `0 Error / 0 Unhandled Rejection`。
   * 若验收发现任何偏差，立即定位修复或一键回滚当前步骤重拆；验收 100% 通过后，向用户出具《1:1 等价性验收报告》，更新 `memory/CODE_MAP.md`，随后方可进入新业务功能开发。

---

### Step 2B：模式 B 执行规程（童子军渐进抽离法则 Boy Scout Rule）

当用户选择 **模式 B** 时，严格遵循**“让每一次触碰过的代码比你来时更干净、局部剥离、全程审批”**的铁律：

1. **精准定位触碰边界**：分析当前用户的业务修改需求，锁定大文件中受影响的目标函数、UI 区块或业务分支。
2. **抽离方案前置审批**：
   * 凡是当前业务修改触碰到的大文件代码块（例如：一个嵌在 3000 行页面里的 120 行弹窗逻辑，或一个嵌在庞大路由文件里的独立计费函数），不得继续往原大文件里堆砌新代码！
   * 必须设计局部抽离方案（说明：拟从原文件第 `X~Y` 行抽离出独立子模块 `path/to/new_module`，并在原位置替换为显式导入调用），通过 `ask_question` 弹窗经用户审批确认。
3. **先安全抽离、再叠加新需求**：
   * **第一步（纯抽离）**：将目标代码块独立为符合乐高规范的新模块文件，原大文件通过 `import` 引用该新模块，验证原有功能 100% 正常无退化。
   * **第二步（改业务）**：在刚刚抽离出的干净、独立的子模块中实施本次新业务需求。
4. **同步刷新代码地图**：记录原大文件缩减后的行号变化与新诞生的独立积木模块，逐步蚕食并消灭历史屎山。

## 三、 活体代码地图（`memory/CODE_MAP.md`）全自动维护规范

为彻底解决跨会话开发时因盲目全局搜索导致的 Token 浪费、改错文件、遗漏上下游依赖以及“阴阳副本”问题，项目必须维护唯一架构导航图：`memory/CODE_MAP.md`。

### 3.1 触发时机与强制审批流程

* **触发时机（100% 必达）**：每当完成**新增文件模块**、**修改既有模块的核心职责/对外接口/行号区间**、或**拆分/删除/移动文件**后，必须在任务收尾前同步提取最新代码结构元数据。
* **五维精准提取指标**：
  1. **模块路径（Module Path）**：相对于项目根目录的规范路径。
  2. **核心职责（Core Responsibility）**：一句话精准概括该乐高模块的单一职责边界（它做什么、不做什么）。
  3. **关键函数/类/组件名与起止行号区间（Key Symbols & Exact Line Ranges）**：通过精确扫描工具获取每个核心导出符号在文件中的精确起止行号（格式如 `calculateInvoiceTotal (L18-L64)`），严禁凭猜测编造行号！
  4. **上下游依赖（Upstream & Downstream Dependencies）**：
     * **上游调用方（Imported By）**：哪些模块依赖了本模块。
     * **下游被调方（Imports）**：本模块显式导入了哪些内部模块或核心外部适配器。
  5. **唯一真源标记（Single Source of Truth, SSoT Tag）**：明确标注 `[SSoT: 唯一真源]`；若项目存在编译构建产物、静态资源分发副本或跨端同步文件，必须明确标注其真源指向与自动同步脚本。
* **强制用户弹窗审批（`ask_question`）**：
  在将提取到的结构变更写入 `memory/CODE_MAP.md` 之前（或生成更新预览后），必须通过 `ask_question` 弹窗向用户展示本次代码地图的变更摘要（新增/修改了哪些模块条目、行号区间更新及唯一真源核验结果），征得用户审批确认后落盘生效。

### 3.2 严禁“阴阳副本”铁律（Zero Duplicate / Shadow Files Policy）

1. **禁止手工维护多份同逻辑文件**：严禁在项目中保留诸如 `service_v2.js`、`service_bak.js`、`utils_new.py` 等命名含糊的平行副本；历史废弃代码既然已有 `scripts/snapshot-and-rollback.sh` 和版本控制保障，必须果断清理，确保同一职责在全库只有**唯一真源（Single Source of Truth）**。
2. **构建产物与镜像副本强制受控**：
   * 若因工程部署架构原因，确实存在从源码生成的静态分发副本、SDK 导出副本或跨目录镜像文件，**严禁直接手动修改副本文件**！
   * 必须在 `memory/CODE_MAP.md` 的专门章节中登记：`[派生副本路径] <--自动同步自-- [唯一真源路径] (同步命令: bash scripts/build-and-sync.sh)`。
   * 任何源码变更后，必须自动执行同步脚本更新派生文件，并在代码地图中核验哈希或时间戳一致性。

### 3.4 账本更新与代码修改中的「精准微靶向修改、先行探测与切片容错」铁律（`EVO-019` & `EVO-020` & `EVO-022`）

1. **`edit_file` 精准微靶向修改（Minimal Unique Anchor 原则，`EVO-019`）**：在更新 `CODE_MAP.md` 或长源码文件时，严禁使用几十上百行的跨章节超长 Target 替换；Target 必须基于最近刚通过 `read_file` 读取的真实行，仅截取待改行及其前后 1~2 行唯一特征上下文（3~10 行以内），不相邻的段落必须分成多次独立调用 `edit_file`，彻底杜绝 `target content not found in the file` 报错。
2. **深层未知文件路径先行探测（Pre-Read Verification 原则，`EVO-020`）**：在存量大代码库中查找模块或执行读取前，严禁凭直觉脑补文件名直接调用 `read_file` / `view_file`；必须优先通过 `CODE_MAP.md` 索引、或运行 `ls` / `git ls-files` 嗅探实证文件已真实存在后再读取，彻底杜绝 `file does not exist` 报错。
3. **会话切片短 ID 软链接与索引精准点读（Session Slice Resilience 原则，`EVO-022`）**：查阅 `memory/sessions/` 切片时，必须点击 `CONVERSATION_INDEX.md` 最后一列提供的完整超链接；系统底层已由 `session-memory-slicer.mjs` 与 `evo-patrol-inspector.mjs` 自动创建 `CONV-YYYYMMDD-XXX.md` 短 ID 软链接做双向容错，严禁凭空臆测不存在的切片文件名。

## 四、 架构执行检查清单（Mandatory Execution Checklist）

在每次执行代码编写、重构或提交任务前，必须逐项核对以下检查单：

- [ ] **【乐高颗粒度核验】**：本次新增或修改的逻辑是否包含独立的 UI 零件、业务服务、数据访问或工具函数？如果是，是否已从第一行代码起就拆分为独立文件模块，而非塞入现有文件？
- [ ] **【备份锚点核验】**：若本次任务涉及旧项目改造或大范围结构拆分，动刀前是否已运行 `scripts/snapshot-and-rollback.sh backup` 并向用户提供了 1 秒一键回滚指令？
- [ ] **【模式审批核验】**：面对历史耦合大文件时，是否已通过 `ask_question` 弹窗让用户明确选择了 **模式 A（全量标准化改造 + 1:1 等价性复现验收）** 或 **模式 B（童子军渐进抽离法则）**？
- [ ] **【无损等价核验】**：拆解或抽离模块后，是否已验证接口输入输出 100% 一致、UI 渲染与交互 100% 一致，且无任何新增编译或运行期警告/错误？
- [ ] **【零阴阳副本核验】**：全库是否不存在任何手工双改的重复文件或未登记的镜像副本？
- [ ] **【精准修改与路径核验】**：`edit_file` 是否遵循最小特征锚点（3~10行以内）？读取文件前是否已通过探测实证路径真实存在？
- [ ] **【活体代码地图更新核验】**：是否已重新提取最新模块的「路径、核心职责、关键函数与精确起止行号区间、上下游依赖、唯一真源标记」，并通过 `ask_question` 征得用户审批后同步更新至 `memory/CODE_MAP.md`？
